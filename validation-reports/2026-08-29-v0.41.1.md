# Validation Report — terrariabonker v0.41.1

**Date**: 2026-08-29
**Scope**: Noticing that the world changed (spec 049), a cache-key bug shipped in v0.41.0,
and a settle gate on everything that writes after a world load.

## Summary

A bug report — "switch worlds with the trainer open and the cheats do not come back" —
turned out to rest on a fact this codebase did not have: **nothing knew which world was
loaded**. The same gap had already shipped a second bug in v0.41.0.

738 tests pass (was 720). Nine mutations run against this release's changes, **eight caught
on the first attempt and one survivor**, recorded below.

## The part worth reading

**The tile buffer and the world dimensions do not identify a world.** Auto-sell's
piggy-bank cache, shipped in v0.41.0, was keyed on `(tile buffer address, max_x, max_y)`.
`AGENTS.md` already recorded that the buffer is allocated at the largest supported size and
reused, and a measurement across a real switch settled it:

| | The Lousy Yeet | Royal Brewery of Maggots |
| --- | --- | --- |
| dimensions | 4200x1200 | 4200x1200 |
| tile buffer | 0x07780c28 | 0x07780c28 |

Byte-identical. The consequence was that auto-sell could carry "a piggy bank is placed
here" across a world switch and pay coins into a bank the player cannot open. Found by
reading the code for the reported bug, confirmed by the maintainer's own world switch.

**`Main.worldName` is at +0x660**, found by diffing Main's 0x4000-byte static block across
that switch: 139 dwords changed and this was the one whose value matched the world files on
both sides. The GUID at +0x148 did *not* change, so it is a session or client id — recorded
so nobody re-investigates it. **`Main.worldID` was not pinned**: +0x160 (116799 -> 128925)
is a plausible candidate and nothing more, and a guessed constant is what this project has
scars from. The known cost is that two worlds sharing a name *and* size would collide.

**Restoring after a cold launch takes about 80 seconds, and most of it is not a fault.**
Measured on a real cold start: game up at 00:08:47, 9 of 15 cheats applied at 00:09:55, all
15 by ~00:10:05.

- Every pass re-resolves the anchors: **14.3 s** cold across 13 unique anchors (0.7-2.1 s
  each; `mining` and `reach` share `reset_block`), against ~5 s warm where 11 are already
  resolved and persisted per-pid.
- Several cheats hook methods mono has not compiled yet. `fast_place`'s method compiles the
  first time the player places a block, so it **cannot** be applied before then.

The fix chosen was reporting rather than optimising: the panel logged once and then went
silent for the remaining ~75 s, which is indistinguishable from a hang. It now says how many
are applied, how many are waiting, and why. Caching scans across pids was deliberately not
attempted — whether a site resolved against one process is valid in another is a question
about the JIT that needs its own measurement.

**Two crashes, neither traced.** The game died twice during structural operations (opening
a chest; a second world reload) with the trainer writing. No managed exception in
`client-crashlog.txt`, no segfault in `dmesg`, no coredump — which is what a native write
into reclaimed memory looks like, and equally what other things look like. The Proton log
that might have carried evidence was overwritten when the game relaunched.

No cause was established and none is claimed. What changed is caution: **nothing is written
to a world that has not been reported unchanged for two consecutive polls**. Both the
restore and auto-sell — the panel's heaviest writer, which was writing into the inventory
and bank chest twice a second straight through both reloads — now wait. A world load is the
moment the arrays being written to are rebuilt, and a sale can wait.

**An instrument error, recorded because it nearly became a finding.** The first probe
written to measure the cold restore read the patch state file without checking whose pid it
was for, found the *previous* game's state, and reported all 15 cheats applied 0.7 s after
launch. It was wrong by ~80 seconds and read as authoritative. Had the maintainer not been
watching the screen, "restore is fast, nothing to fix" would have gone in this report.

## Tests

738 pass. New: `test_world_change.py` (18). `test_sell_panel.py` gained a settle helper,
since the panel now writes nothing to an unsettled world.

`MAIN_WORLD_NAME_OFF` is pinned as a literal with its provenance in the docstring.

### Mutations

| # | Mutation | Result |
| --- | --- | --- |
| M23 | key the world on `(buf, max_x, max_y)` again | caught |
| M24 | restore on a new pid only (the reported bug) | caught (2 tests) |
| M25 | treat an unreadable world as a world change | **survived**, then killed after rewrite |
| M26 | do not validate the world name | caught |
| M27 | restore on the first sighting, no settle | caught (2 tests) |
| M28 | never reset the settle counter | caught |
| M29 | auto-sell ignores the settle gate | caught |
| M30 | report progress on the first pass only | caught |
| M31 | drop the explanation from the progress line | caught |

M25's test fed only `None`, so both versions settled after one restore and the mutant
survived. The case that separates them is a world that is *transiently* unreadable, which
is what a load screen looks like; rewritten around that, the mutant dies.

## Code quality

`Service._static_base` was extracted because `world_id()` runs on every status poll and was
calling `main_static_base` directly — a full memory scan costing ~1.5 s, once per second.
`tilemap()` now shares the same cached answer.

## Security review

- No new runtime dependencies; `requirements.txt` unchanged, so no `pip-audit` run.
- No `eval`/`exec` of dynamic input, no shell strings, no network calls, no secrets.
- The new read is one mono string from Main's static block; the new gate only ever
  *prevents* writes.

## Release safety

**Rollback**: one commit. `world_id()` fails safe — a rotted offset returns None and both
callers fall back to their previous behaviour (restore on pid change, re-scan the world)
rather than acting on a wrong answer.

## Live verification

Confirmed by the maintainer after this report was first written: loading into a new world
with the trainer running brings the saved cheats back on its own, which is the bug spec 049
was opened for. Spec 049 is COMPLETE.

## Known gaps

- `Main.worldID` is unpinned, so two worlds with the same name and size collide.
- **The two crashes are unresolved and did not reproduce.** A later play session on this
  build could not trigger either one. That is not evidence they are fixed: both were
  one-off deaths during structural operations, nothing about them was ever traced, and a
  race that fires twice in an afternoon and then not at all is behaving exactly as a race
  does. The stale-address bug they prompted was real and is fixed on its own merits; the
  container race is unmeasured and now unguarded by choice. The settle gate narrows the
  window at a world load and does nothing for a chest opened mid-play, which is what the
  first crash looked like.
  **If it recurs: do not relaunch the game.** `PROTON_LOG=1` is enabled, so
  `~/steam-105600.log` holds wine's view of the fault — the layer that would show a native
  crash, and the one piece of evidence both crashes lacked. Relaunching overwrites it. (It
  reached 9.6 GB in a session, so it is worth watching the disk.)
- A cold restore still costs ~80 s. It is now narrated rather than silent.
