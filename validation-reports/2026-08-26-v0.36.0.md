# Validation Report — terrariabonker v0.36.0

**Date**: 2026-08-26
**Scope**: Auto-use (spec 043) — press the player's use button once, from inside the frame
— and auto-catch built on it, which reels in every bite and casts again between them.

## Summary

The first new code injection since the arena migration, and the first cheat in this project
that acts *for* the player rather than changing a number they then act on.

It works: 20 arms produce 20 presses, one bite produces one fish, and a session of
autofishing ran 23 catches from a single manual cast. The stub is about fifteen
instructions, calls nothing, and its CPU cost is unmeasurable against the cheat being off.

The release is worth reading for its failures rather than its feature. **It crashed the
maintainer's game once, published a false finding, and shipped a flag that did nothing** —
and each of those was caught by a different mechanism: the game dying, the maintainer
noticing they were the one clicking, and a measurement being re-run under better conditions.

## The part worth reading

**The bite signal came out of the game's own code, not out of memory diffing.** Two earlier
sessions hunted a "catch counter" by sampling the bobber and the player, and both failed.
Reading `Player.ItemCheck_PullFishingBobbers` with `tools/ilrecon` settled it in an
afternoon: a bite is `ai[0] == 0 && ai[1] < 0 && localAI[1] != 0` on the player's bobber,
which is the game's own pull condition. The counter that two probes could not find is
`localAI[1]` — behind a `float[3]` reference, so scanning the object's own bytes could
never have seen it. **Read the code before diffing the memory.**

**Two arena collisions, same root cause.** Arena slots were indexed by `sorted(INJECTIONS)`,
so adding an injection whose name sorts first moved every other slot by 0x800 — and the new
stub was written straight over a *live* one in an arena left from the running session. The
game ran on with corrupted control flow and died a few frames later on a null dictionary in
unrelated code. Then, separately, auto-use's arm word was placed at arena `0x500`, inside
the ore extractor's queue (`0x400`–`0x504`): mining a vein wrote the extractor's tile count
into the arm flag, and the stub pressed the player's use button for every batch queued.

Both came from choosing a constant without reading what was already there. `_SLOT_ORDER` is
now append-only, the stamp is bumped so an arena laid out by the old numbering is not
adopted, a pre-flight refuses to write a stub into a slot holding anything but padding, and
the data offsets are covered by a test that computes the extractor's extent rather than
trusting a comment.

**A false finding was published and then withdrawn.** "The stub cannot cast, only reel" was
written up with a plausible mechanism — casting needs `controlUseItem` *and*
`releaseUseItem`, the stub writes only the first — and `--recast` was removed on the
strength of it. Both halves of the evidence were bad: the test asked for a rod to be
selected without verifying it, and the water was never empty because `find_bobbers`
filtered on `bobber` alone. A projectile the game has finished with keeps its old fields, so
a reeled bobber read as still cast for fifteen seconds and more. With `Projectile.active`
(`+0x03C`) checked as the game checks it, one press casts: 2/2, then 23/23 in play.

**The maintainer found the bug no scripted test would have.** With "and cast" on, the cheat
recast *anything held* — it looked at the water and never at the hand. Fixed twice over: a
cast that produces no bobber closes the gate (needs no new knowledge, covers reasons not
yet thought of), and nothing is pressed on empty water unless a rod is held
(`Player.selectedItem` at `statLife-0x694`, found by watching which ints tracked the hotbar
and checking each against the slot the player was on).

from 476 at v0.35.0.

## In-game verification

All nine acceptance criteria on spec 043, on 1.4.5.8+24893155:

- **Exactly one press per arm**: 20 arms → 20 presses; nothing at all while disarmed.
- **One fish per bite**: the bobber count never moved, where the old poller's 20 ms burst
  took the water from one bobber to three.
- **A full session**: 23 fish over 250 rounds from one manual cast, reeling and recasting.
- **It stops when the rod leaves the hand**, and starts again on the next cast with no
  toggling — verified by the maintainer in play, and by a probe that watched the press
  counter stay flat across seven item switches.
- **Title screen**: armed 50 times at the main menu, zero presses, game unharmed. The stub
  takes `this` from `Player.Update`'s frame, so it cannot run without a player.
- **CPU**: 19.70 ms per 1000 frames with the cheat on and 19.70 with it off, medians equal
  and ranges overlapping across four alternating windows each.

## Security review (Phase 5)

- No `eval`/`exec`, no `subprocess`, no sockets, no network calls in shipped code.
- No hardcoded credentials.
- Dependencies unchanged since v0.34.0, so `pip-audit` was not re-run.
- The new writes are: five bytes at one hook site, a stub in memory the trainer allocated,
  and one byte per press in the player's own object. Nothing is written to the world or the
  save, and nothing new is written to disk.
- **This cheat can act as the player.** It presses "use the held item", which with a weapon
  is an attack. It ships switched off, its label says what it does rather than what it is
  for, and auto-catch refuses to press unless a rod is held.

## Release safety

- **Rollback**: disabling restores the 13 displaced bytes with the game running; `git
  revert` or the previous tag otherwise. Nothing touches the world or the save.
- **The arena stamp moved to `TBARENA2`**, so a trainer from this version ignores an arena
  laid out by an older one and allocates a fresh 64 KB. That is deliberate: adopting the old
  layout is what wrote a stub over a live one.
- A press promised but not yet landed is dropped when the cheat is switched off, and the
  arm word is cleared on enable — an arena outlives the trainer, so a stale arm would fire
  on the first frame of the next world.

## Known gaps

- **The arena bootstrap springboards off `ore_extract`'s own injection site**, so it cannot
  allocate an arena while that cheat is enabled. Latent for months; exposed by the stamp
  bump. The workaround is to disable the extractor once, and the fix is a springboard site
  that is not also a cheat's hook site.
- **`RELEASE_ITEM_OFF` (`Player+0x67F`) is not identified.** The stub writes it, and casting
  works without it, so it is not load-bearing — it is a byte with the right shape and
  nothing more. Setting the arena word to 0 falls back to the control byte alone, which is
  what every measurement here was taken with.
- **The call target at the hook site is identified by shape and position**, not by mono
  metadata. That does not affect the hook, which needs only a per-frame site with `this` in
  the frame.
- **One cast in a session came back unconfirmed** as the maintainer switched items. It costs
  one press and closes the gate, which is the designed behaviour, but the cause was not
  established.
