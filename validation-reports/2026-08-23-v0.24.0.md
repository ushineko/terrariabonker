# Validation Report — terrariabonker v0.24.0

**Date**: 2026-08-23
**Scope**: Spec 034 — clamp the smart-cursor search range.

## Summary

Holding Shift to auto-place collapsed the frame rate with the reach cheats set high.
`SmartCursorHelper.SmartCursorLookup` sizes its search region with
`TileReachCheckSettings.GetTileRegion`, which calls the `GetRanges` that `tool_reach` forces
and then adds `blockRange` on top. The region is an area, so both reach cheats stack into a
quadratic cost: ~121 tiles a frame at vanilla-ish reach, 22,801 at 75, roughly 90,000 with
both at 75.

The clamp could not go in `GetTileRegion` — nine callers, including
`IsInTileInteractionRange` and `AdjTiles`, the ones `tool_reach` exists to extend. It goes at
the tail of `SmartCursorLookup`, narrowing the four `SmartCursorUsageInfo` region fields after
the game's own world-edge clamps, so placement reach and tool reach are untouched.

## The part worth reading

The four fields serve **three** purposes, and only the first is visible in the IL:

1. the extent the smart cursor searches;
2. the "is the cursor within reach" test five instructions later — fail it and the game
   abandons smart cursor entirely;
3. the working area of a search that runs outward from the player.

Two clamp shapes were built, shipped to the live game, and rejected by play:

- **Centred on the player.** Broke (2): moving the mouse past the radius put the cursor
  outside the box. Reported as "it places, then moving the mouse starts placing without smart
  enabled."
- **Centred on the cursor.** Satisfied (2) but broke (3): the span back toward the player was
  cut out, so the torch chain stopped forming once the two were more than the radius apart.

The shipped shape spans both ends — the original box's midpoint is the player tile, the
cursor comes from `screenTargetX/Y`, and the clamp keeps `min-N .. max+N` intersected with
the original box so it can only shrink. Neither wrong shape was detectable from the IL or
from any test that could be written; both were found by the maintainer playing.

## Phase 3 — Tests

- **226 passed** headless, up from 215.
- `tests/test_smart_cursor.py` (11): the displaced store is reproduced first and the displaced
  `test ebx,ebx` last (the following `je` branches on its flags); the radius is baked in four
  times per stub; a zero/negative radius floors to 1; only the four `reachable*` fields are
  touched; enable installs a jump and disable restores; retuning rewrites the stub without a
  re-enable; the anchor still resolves with the cheat applied; it lands in the Build section;
  and the box provably covers both the player and the cursor ends.
- The stub was disassembled against the live game before each of the three attempts.
- **Live, maintainer-verified**, with `reach`/`tool_reach` left at **75**:
  - the stutter is gone — and it had been triggerable by *holding Shift alone*, i.e. by the
    per-frame search rather than by placing;
  - manual placement reach is unchanged;
  - tool and interaction reach are unchanged (the criterion that would have proven the design
    wrong, since those paths use `GetTileRegion`'s other callers);
  - smart placement itself behaves normally at range.

## Phase 4 — Code quality

- Anchor found by call graph rather than constants: `tool_reach` already anchors `GetRanges`;
  its callers lead to `GetTileRegion` (identified by having six JIT'd callers), whose callers
  lead to `SmartCursorLookup` (identified by the four `Utils::Clamp` blocks against
  `maxTilesX`/`maxTilesY`). Recorded in `ce/SMARTCURSOR_FINDINGS.md`.
- The anchor wildcards exactly what the cheat displaces, so a cold re-resolve works with the
  cheat applied — covered by a test, as for specs 032 and 033.
- The two rejected shapes are documented in `_shrink_smart_cursor`'s docstring, because the
  reason they failed is invisible in the code they patch.
- The spec's technical section was corrected to describe what shipped; it had specified the
  first, rejected shape.
- flake8 clean at the project's ~100-col convention on changed files.

## Phase 5 — Security review

- No `eval`/`exec`, no shell, no network, no new dependencies. `pip-audit 2.10.0`: *No known
  vulnerabilities found*.
- The stub is fixed opcodes plus the user's radius as an immediate, floored at 1; the byte
  length does not vary with the value.
- Writes confined to the resolved anchor site and a borrowed int3 cave through the existing
  machinery; disable restores the bytes and scrubs the stub.

## Phase 5.5 — Release safety

- **Rollback**: `git revert`; the cheat is off by default and disable restores the original
  smart-cursor behaviour. A game restart clears it.
- **No save-format change**; it only narrows a search the game performs each frame.
- **Ledger**: the anchor is recorded as verified on `1.4.5.7+24893155` only.

## Known limitations

- **Spec 034 remains INCOMPLETE by one criterion**: behaviour when `SmartCursorLookup` has not
  been JIT-compiled yet is unverified — it was already compiled in the session this was built
  in. By design it reports "matched nothing" honestly and auto-restore retries, but that is
  reasoning, not evidence. To be confirmed on the next fresh game launch.
- **The CPU measurement used for spec 033 was deliberately not repeated**: the interleaved A/B
  method needs the workload sustained for ~80 seconds, which here means holding Shift
  throughout. The in-play result is unambiguous, so the subjective confirmation stands as the
  evidence.
- **Shrinking the box changes behaviour, not only cost.** The smart cursor considers a smaller
  area; the value is exposed so the user can trade back.

## Result

Gates pass, with the one open verification item recorded above. Approved for commit and tag
`v0.24.0`.
