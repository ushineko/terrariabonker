# Validation Report — terrariabonker v0.40.0

**Date**: 2026-08-27
**Scope**: A shipped offset bug that had been wrong since the first projectile work, the
runtime-metadata tool that found it, and the projectile editor the correction unblocked
(spec 047).

## Summary

One new cheat and one real bug fix, but the substance of this release is a method change.
Every offset in this project used to be *derived* — from declaration order, from a value
signature in `SetDefaults`, from watching a number change in game. This release replaces
that with asking the mono runtime directly, and the first thing the new tool did was
disprove a constant that 617 tests, 23 unattended fish and several hours of play had all
agreed with.

651 tests pass. Nineteen mutations run against this release's changes, **all nineteen
caught**.

## The part worth reading

**`Projectile.active` was `Entity.wet` for eight releases.** Read at `0x03C`, which is the
wetness flag; the real offset is `0x078`.

Nothing caught it, and the reason is the finding. The only projectile this project ever
looked at was a fishing bobber — and **a bobber floats in water, so `wet` is true exactly
when a live bobber exists.** The wrong offset was indistinguishable from the right one
across the entire feature that used it. The first thing to disagree was a projectile that
flies through air.

Consequences, all recorded in `docs/item-fields.md`:

- Every projectile probe ever run was blind to anything not underwater. The v0.39.0
  collision A/B (30.7% vs 0.9%) is void; it sampled only wet skulls.
- "The skulls get bigger the moment they hit the water", reported from play and filed as a
  coincidence, was the truest reading anyone took: the probe could only *find*, and so only
  *patch*, wet projectiles. The size change appeared at the waterline because that is where
  each skull became visible to the tool.
- The maintainer was twice told they were not firing, against their explicit correction
  both times. They were firing on both occasions.
- **Expected but unconfirmed**: bobber detection should have been broken in lava (Hotline
  Fishing Hook) and honey, where `lavaWet`/`honeyWet` are set and `wet` is not. Listed
  under Known gaps — the fix predicts it works now, and nobody has tested it.

**`tools/monofields.py` asks the runtime instead of inferring.** `MonoClassField` on 32-bit
is `{type, name, parent, offset}`, so finding a field-name string and then a pointer to it
puts the offset 8 bytes on. It deliberately does not walk `MonoVTable` or `MonoClass`,
whose layouts shift between mono builds; avoiding them is what should let it survive a game
update.

`--verify` checks 42 offsets across `Entity`, `Projectile`, `Item` and `Player` and exits
non-zero on disagreement. All 42 currently agree. It settled several long-open questions at
once:

| Field | Believed | Runtime |
|---|---|---|
| `Projectile.active` | `0x03C` (= `wet`) | **`0x078`** |
| `Projectile.hostile` | unresolved, briefly `0x030` | **`0x0C8`** (a bool) |
| `Item.armorPenetration` | predicted `0x154`, unwritten | `0x154` — confirmed |
| `Item.bonusTagDamage` | predicted `0x158`, unwritten | `0x158` — confirmed |
| `Item.reuseDelay` | unknown | **`0x164`** |

The two `Item` fields v0.39.0 declined to write were right all along. They stay unwritten:
verifying an offset removes the reason to refuse, but writing new fields into saved items is
a behaviour change and belongs to a spec.

**The self-referential test problem, now addressed.** A fixture planted through a constant
and read back through the same constant proves only that the constant equals itself. That
is how `active` survived, and how a mutation moving `crit` one field along passed the whole
suite in v0.39.0. Offsets are now pinned as **literals** with their provenance in the
docstring, and `--verify` re-checks them against a running game.

**Terrain ages the Book of Skulls, it does not stop it.** Reported from play: the skulls
cross some tiles but not all, despite `tileCollide = 0`. `AI_001` special-cases type 837 to
subtract 33 ticks of `timeLeft` for every tick the projectile's centre is inside solid tile.
It spawns with 480, so roughly nine tiles of stone exhausts it. `penetrate` (3) is the NPC
pierce count and never decrements on tiles.

The general warning, now in `AGENTS.md`: **a projectile's observable behaviour is not
necessarily governed by the field that appears to name it.** `AI_001` writes `tileCollide`
in 13 places and reads it in none.

## The projectile editor (spec 047)

A Projectiles tab: pick a weapon, see the projectile it fires, and change what that
projectile does while you play — pass through blocks, enemies pierced, extra ticks per
frame, size, lifetime.

**Why it is a sweep and not an edit.** `SetDefaults` assigns literals and never consults
`ContentSamples.ProjectilesByType`, so there is no write that makes a projectile change
stick. Every field is re-applied to each live projectile from a 50 ms tick, the way vein
watching and auto-catch already work.

**A hazard the spec did not anticipate**, found while implementing: enforcing `timeLeft`
every sweep stops projectiles ever expiring, and the game allocates all 1001 slots up front
— so a pinned lifetime fills the array and the player's weapons quietly stop firing.
`timeLeft` is applied **once per projectile** instead, which is also what the Book of Skulls
actually needs given the drain above.

**`penetrate` carries `maxPenetrate`.** Settled from the IL rather than assumed:
`SetDefaults` ends with `maxPenetrate = penetrate` as its final statement.

**Five fields, and the exclusions are deliberate.** The metadata walker makes it trivial to
offer all 118 `Projectile` fields, and most of them are a crash or a self-inflicted death.
`aiStyle` runs an AI against `ai[]` slots that mean something else; `hostile`/`friendly`
turn the player's own projectiles on the player. Neither is reachable by any path, and the
CLI parser refuses them by name rather than dropping them silently. Values are clamped where
they are written, not in the widget.

**Verified in game by the maintainer**, which spec 047 required as an integration-boundary
criterion. The before-value the criterion asks for came from the recon A/B: `BoneGloveProj`
read `tileCollide = 1` on 20 of 20 newly-seen projectiles, and forcing 0 moved it from 10.6%
to 57.5% of samples inside terrain against a slot-parity control. That check exists because
the opposite case cost an afternoon — the Book of Skulls already ships with
`tileCollide = 0`, so every earlier session enforced a value the game had set itself.

**A leak a test found.** Setting the selected projectile type and reloading the controls
were two steps, so switching weapons left the previous weapon's boxes ticked and the next
edit wrote them onto the new projectile, with nothing on screen to say so. They are one
method (`_pj_select`) now.

## Tests

651 pass (`pytest`, headless, against the synthetic memory image — no game, no root). Up
from 617 at v0.39.0. `flake8` clean on changed files apart from three known pre-existing
violations (`cli.py`, `client.py:19`, `test_locate.py:4`).

Nineteen mutations, all caught:

| Mutation | Outcome |
|---|---|
| `active` read as `Entity.wet` again (the shipped bug) | caught |
| `active` off by one field | caught |
| `crit` written to the unverified neighbour offset | caught |
| a bool written four bytes wide (clobbers its neighbour) | caught |
| `timeLeft` pinned every sweep (projectiles never expire) | caught |
| `penetrate` written without `maxPenetrate` | caught |
| values reach the game unclamped | caught |
| projectile identity by slot index instead of by object | caught |
| inactive projectiles patched too | caught |
| overrides applied to every projectile type | caught |
| the pass-through checkbox stores 1 (collide) instead of 0 | caught |
| an emptied weapon keeps an entry that enforces nothing | caught |
| selecting a weapon leaves the previous one's boxes ticked | caught |
| the panel polls the worker with nothing to write | caught |
| switching off leaves per-projectile state in the worker | caught |
| overrides are not saved on close | caught |
| overrides are not restored on start | caught |
| saving overrides wipes the window size and Effects | caught |
| projectile types stay strings after a reload | caught |

Three of those were survivors on the first pass, all because the test was not observing the
path it claimed to: the panel tick goes through `helper.request` rather than `_call`, and
neither `closeEvent` nor the restore path had a test at all. Recorded because "caught" after
fixing the test is a different fact from "caught" first time.

One **equivalent** mutant, recorded as a finding rather than counted: removing the
`helper.available` guard from the panel's tick changes nothing observable, because
`request()` already returns `False` when the worker is down and the caller resets its
in-flight flag on that return.

**A process note.** The first mutation run was killed by a command timeout and left a mutant
in the working tree; a `pytest` run overlapping it reported two spurious failures. Only
`git diff` caught it. The runner now restores on `SIGTERM`/`SIGINT` and via `atexit`, and
mutation runs go in the background where a timeout cannot interrupt them.

## Security review (Phase 5)

- No `eval`/`exec`, no subprocess, no sockets, no network calls in the new code.
- No hardcoded credentials.
- Dependencies unchanged since v0.34.0, so `pip-audit` was not re-run.
- `tools/monofields.py` is **read-only** — `/proc/<pid>/maps` and `/proc/<pid>/mem` reads,
  no writes to the game at all.
- **New writes to the game**: projectile fields, on live objects only. This is the safest
  write surface in the project — projectiles are transient and never saved, so the blast
  radius is a session and switching off restores nothing because there is nothing to
  restore. Values are clamped at the point of writing so a number typed into a spin box
  cannot reach the game unbounded, and bools are written one byte wide so a write cannot
  reach the field packed behind it.
- `tools/projectile_probe.py` still writes to live projectiles, requires root, and is
  opt-in. Its `active` offset and bool widths are both fixed here.

## Release safety

- **Rollback**: `git revert` or the previous tag. No patch changes, no arena stamp change
  (`TBARENA2` since v0.37.0), no save-format change. Projectile overrides are added as a new
  key in the existing GUI state file and merged rather than replacing it, so an older build
  ignores them harmlessly.
- **Nothing written by the new cheat needs rolling back.** Unlike the v0.39.0 modifier work,
  which writes item stats that persist, this release's writes vanish with the projectile.
- **Behaviour change**: bobber detection now gates on `active` rather than `wet`. For water
  fishing this is identical; for lava and honey it should be a fix. No regression path is
  known, and `read_bobber` still checks `bobber` as well.

## Known gaps

Carried forward:

- `RELEASE_ITEM_OFF` (`Player+0x67F`) is still unidentified.
- The auto-use hook's call target is identified by shape and position, not mono metadata.
- Whether switching items destroys an outstanding bobber was never settled.
- `Service` and `MainWindow` remain god classes (spec 045 tiers 2–3, deferred by design);
  this release adds ~200 lines to `MainWindow`.
- `service.py`'s deferred imports are unchanged; the rule in `AGENTS.md` binds new code.
- `Item.armorPenetration` / `bonusTagDamage` / `reuseDelay` are verified but still unwritten.

New with this release:

- ~~**Lava and honey fishing are untested.**~~ **Closed 2026-08-27, after tagging**:
  auto-fishing confirmed working by the maintainer in both lava (Golden Fishing Rod, Magma
  Snail bait) and honey. See the addendum.
- **The projectile editor is single-player only.** These writes are local and would desync a
  server, as the rest of the project assumes.
- **A one-frame window** before the first write: a projectile acts on its own defaults for
  up to one poll interval. Invisible for `tileCollide`; unmeasured for anything affecting
  spawn behaviour.
- **Weapons sharing a projectile type edit each other.** Named in the UI rather than
  prevented, because it is a property of the game and not of the editor.

## Addendum — 2026-08-27, after tagging

**Lava and honey fishing confirmed.** The one Known gap this release opened is closed:
auto-fishing works in lava (tested with a Golden Fishing Rod and Magma Snail bait) and in
honey.

This was predicted from the field layout rather than observed — `lavaWet` (`0x040`) and
`honeyWet` (`0x03E`) are separate from `wet` (`0x03C`), so a bobber floating in lava read
`wet = 0` and was invisible to a check gated on the wrong byte. Auto-catch should have been
broken in lava for every release before this one, and nobody had tried it.

Recorded because it is the only model in this investigation that was reasoned out *before*
being measured and still held. The rest — `active` at `wet`, `hostile` at `0x030`,
`tileCollide` as the reason skulls cross walls — were all confidently wrong. The difference
is that this one was derived from a layout the runtime had already confirmed, rather than
from inference about a layout nobody had checked.

Honey was the follow-up prediction from the same layout — `honeyWet` at `0x03E`, adjacent
to `wet` — and it held as well. Both liquids are now results rather than predictions, and
this gap is fully closed.
