# Validation Report — terrariabonker v0.32.0

**Date**: 2026-08-24
**Scope**: Spec 040 — the ore extractor, and the memory allocation it needed. Plus two
inventory bugs found by playing it, and honesty repairs to the build ledger and the README.

## Summary

Break one ore block by hand and the connected vein goes with it — at extended reach,
including falling silt piles. It is the first cheat here with no existing behaviour to
widen: vein mining needs a flood fill and a whitelist the game never does in one place.

Getting there needed memory of our own inside the game, which retires the borrowed-padding
technique every previous cheat has relied on.

## The part worth reading

**Four wrong diagnoses.** The stub crashed the game on every attempt, and each hypothesis
fitted the evidence before a test could separate it from its rivals: runaway recursion
through the re-entrancy guard (a real bug, fixed, but a single queued tile cannot recurse
and still crashed); stack misalignment (real, fixed, but `teleport` hands its callee
`esp ≡ 8` and has never crashed); a bad `this` (checked against the object `live_block()`
resolves — identical, same vtable). What settled it was not more reasoning but wine's own
SEH tracing (`PROTON_LOG=1`), which named the faulting instruction in one run:

```
page fault on WRITE access to 0x7795424b in wow64 32-bit code (0x77954216)
  =>0 0x77954216 in cuesdk_2015 (+0x4216)
```

Both addresses were ours. `0x77954216` was `inc dword [esi+0x3c]`, the state write;
`0x7795424b` was the slot. `_find_cave` had borrowed padding inside a **code section of
CUESDK_2015.dll** — read-execute. Installing worked because `/proc/pid/mem` bypasses page
protection; the CPU running the stub does not. `ore_extract` was the first stub here to
keep mutable state in its cave, which is why nothing had hit it before.

A debugger would have been worse than useless: mono uses SIGSEGV as ordinary control flow
for null checks and GC write barriers, so "break on access violation" trips constantly on
healthy execution.

**Memory of our own.** `Patcher.arena` makes the game call `kernel32!VirtualAlloc` for us
and hands back 16KB of RWX. The address is fixed rather than returned, because a stub in a
read-execute cave has nowhere to report a return value to; the base is chosen from a
verified-free 64KB-aligned hole and found again in `/proc/pid/maps`. It is stamped so a
later run adopts it instead of bootstrapping twice. Every constraint that had been fighting
us — stub too big for a gap, stub may not write, queue fits in no gap — was a consequence
of borrowing, and they went together. This is the graduation `_find_cave`'s own docstring
has always pointed at.

**Hooked per-frame, not per-swing.** At `PickTile` the stub only ran while the player was
swinging, but the queue is armed *after* a swing has broken a tile — so a vein sat armed
until they happened to swing again, and breaking one block and stopping did nothing. It now
hooks `Player.Update`'s per-frame call to `GrabItems`. That also removes re-entrancy
entirely, since `PickTile` is no longer hooked.

**Three performance cliffs, each found by measuring rather than reasoning.** The first
optimisation was aimed at the wrong thing; profiling the loop's components took one command
and found the real cost immediately.

| symptom | cause | fix |
| --- | --- | --- |
| "takes a few tiles" | the watcher rescanned 32k tiles a round (0.29s) | re-check known ore only (0.012s), 18x |
| "still a significant delay" | `tilemap()` called `main_static_base()` — a full scan — per trigger | cache the base: 1510ms → 0.1ms |
| watcher silently stopped | window 45 tiles while `tool_reach` is 75 | window derives from the live reach |

**Two bugs found by playing it, after it "worked".** A vein dug through the ground into
unrelated deposits below — "ore suddenly flying at me from below, long after I stopped
mining" — because the search that follows a falling silt pile ran down the column to the
world floor. And editing the last hotbar slot was refused for holding a Green Torch while
the game showed a plain one: the guard read `_all_inventories()[0]`, an arbitrary player
copy, while `inventory()` reports the live one. The comment justifying that — *"copies are
identical"* — was simply untrue. `give_item` had the same bug and it was worse: it chose a
slot empty in a snapshot and occupied in the game, landing on a real item.

## Phase 3 — Tests

- **395 passed** headless, up from 353 at v0.31.0.
- Mutation-checked throughout (~25 mutations). The ones that matter:
  - a stub writing into its own cave — the crash itself;
  - a variant replacing an anchor's pattern rather than joining it;
  - `give_item` reading a stale copy, which destroys a real item;
  - the watcher rescanning every round, asserted by **counting memory reads**, because
    reintroducing a rescan looks harmless and costs 18x;
  - a batch cap removed, and `esi` advancing 4 instead of 8 — both would mine coordinates
    nobody asked for.
- Two mutations initially **missed**, and both were the test's fault, not the code's: a
  single test let whichever guard ran first mask the other. Split into one test per guard.

## Phase 4 — Code quality

- The watch loop is one `_VeinWatch` object driven by both the CLI (`extract --watch`) and
  the panel (`watch_tick`), so the two cannot drift.
- `_all_inventories` is now documented as **write-only**; reads go to `_live_inventory`.
- flake8 clean on changed files; two pre-existing long lines remain in untouched code.

## Phase 5 — Security review

- No `eval`/`exec`, no shell, no network, no new dependencies. `pip-audit` against
  `requirements.txt`: *No known vulnerabilities found*.
- The review found an `exec()` in a test written this session — it scraped a line out of
  the source and evaluated it. Replaced with a behavioural test.
- `Injection.writes_cave` makes `_find_cave` demand a writable page for any future stub
  that writes, so this class of fault fails at install rather than mid-game.

## Phase 5.5 — Release safety

- **Rollback**: `git revert`. The extractor is off by default and holds no state; disabling
  restores the displaced bytes and disarms the queue with the game still running.
- The arena is leaked deliberately on disable (16KB, process-lifetime) rather than freed,
  because freeing memory another thread might still be executing is the riskier operation.
- **Not reversible for the user**: a mined tile is a permanent change to their world. This
  is stated in the README, the panel note and the spec.

## Known limitations

- **No variants exist yet.** Per-build anchor patterns are implemented but unexercised —
  every release so far has left the patterns matching.
- **The ledger says nothing about the runtime for existing entries.** Runtime tracking
  starts here; older verifications predate it and report none, which is the truth about
  them. Backfilling would be a guess dressed as provenance.
- **macOS is untested and unclaimed.** Same assemblies, different runtime again.
- **A pile falling through a gap** can still land beside a different deposit. The
  "a vein cannot grow" cap bounds the damage.

## Result

Gates pass. Approved for commit and tag `v0.32.0`. Spec 040 COMPLETE.
