# Validation Report — terrariabonker v0.29.0

**Date**: 2026-08-23
**Scope**: Spec 037 — more than one pylon per biome.

## Summary

Terraria allows one pylon of each type. Removing that lets you build a pylon network with
several waystations in the same biome. Three bytes at one method entry, confirmed in play.

## The part worth reading

**The recon question was whether the rule is checked in one place or many.** One, for
single-player: `TETeleportationPylon.PlacementPreviewHook_CheckIfCanPlace`, eleven IL
instructions. `HasPylonOfType` has exactly two callers — this hook and the multiplayer
`NetPlaceEntityAttempt` — so patching the hook is narrower than patching the predicate and
leaves multiplayer's rule intact.

**The polarity had to be read, not assumed, and it is inverted from the name.** A method
called `CheckIfCanPlace` returns **1 when placement is forbidden**: it is registered as
`PlacementHook(hook, badReturn: 1, …)` and `TileObject.CanPlace` rejects when the hook's
return *equals* `badReturn`. Patching it to return 1 would have banned pylons outright
rather than unlocking them, so a test pins the stub to zero and the mutation that flips it
fails that test.

**The second question was whether anything downstream assumes uniqueness** — a placement
that succeeds but never shows on the map would be worse than no cheat.
`UpdatePylonsListAndBroadcastChanges` rebuilds the pylon list by walking every pylon tile
entity and adding each with its own position and type, with no dedupe. The recon said
duplicates should work; play confirmed it.

**Locating the JIT'd method: the scan failed, CE took seconds.** A blind shape-scan of the
executable pages looked for a short method with two calls, matching the IL. It found nothing,
because **`GetPylonTypeFromPylonTileStyle` is inlined** to two `movzx` — the compiled method
contains one real call, not two. `ce/poc_pylon.lua` (following `poc_spawner.lua`) resolved it
via `mono_findMethod` + `mono_compile_method` immediately. Worth remembering: when a method
has to be found by name, reach for `ce/` first.

```
+00  55 8B EC 83 EC 18     push ebp; mov ebp,esp; sub esp,0x18   <- patched to 31 C0 C3
+18  8B 45 14              mov eax,[ebp+0x14]     ; the style argument
+1B  0F B6 C0 / 0F B6 C8   movzx (GetPylonTypeFromPylonTileStyle, inlined)
+21  8B 05 <Main.PylonSystem>                     ; Main-static +0xAF0
+33  E8 <HasPylonOfType>
```

`GetPylonTypeFromPylonTileStyle` ends `C9 C3` — `leave; ret`, no `ret N` — confirming cdecl,
so the bare `ret` in the stub correctly leaves the caller to clean the arguments.

## Phase 3 — Tests

- **347 passed** headless, up from 342.
- `tests/test_patcher.py` (+4): the stub returns zero and contains no `mov eax,1`; the patch
  sits at the method entry with `orig` = `55 8B EC` and the same length as its replacement;
  the anchor wildcards the bytes the cheat overwrites; it lands in the Build section.
- `tests/test_build_ledger.py` (+1 and a new category): `pylon_place` was derived on 1.4.5.8
  and never existed on the older builds, so it claims neither the derivation build nor the
  2026-08-23 rebuild. It sat in an `UNPROVEN_ANCHORS` set claiming **nothing** until it had
  been watched working; that set is kept, now empty, for the next such anchor.
- **Mutation check**: flipping the stub to return 1 fails the polarity test. That is the one
  mistake that would ban pylons rather than unlock them.
- **Live**: the anchor resolves to `0x1AA549E0`, exactly the address CE reported, and
  uniquely; enabling writes `31 C0 C3`; a cold re-resolve with the cheat applied still finds
  the site, so it can be turned off after a restart; disabling restores `55 8B EC` byte for
  byte.
- **Maintainer-confirmed in play**: a second Cavern pylon placed alongside an existing one,
  both drawn on the map and wired into the pylon network.

## Phase 4 — Code quality

- The cheat reuses the existing `Cheat` path — anchor, `patch_off`, `orig`, `patched` — and
  adds no new machinery. No code cave, because the prologue is replaced rather than displaced.
- The anchor comment records why the first three bytes are wildcarded, which is the trap
  specs 032-034 each hit.
- `ce/poc_pylon.lua` is committed beside the other spikes so the resolution is reproducible.
- flake8 clean on changed files; the same three pre-existing hits remain in untouched lines.

## Phase 5 — Security review

- No `eval`/`exec`, no shell, no network, no new dependencies. `pip-audit 2.10.0`: *No known
  vulnerabilities found*.
- The write is **three bytes at one resolved anchor site**, of fixed content and length, and
  disable restores them. Nothing is computed from user input.
- The CE script is read-only: it resolves and reads, and writes nothing to the game.

## Phase 5.5 — Release safety

- **Rollback**: `git revert`; the cheat is off by default, disable restores the bytes, and a
  game restart clears it.
- **No save-format change.** Pylons are ordinary tile entities. A world with several of a
  type loads in vanilla, where the extras simply cannot be replaced once broken.
- **Ledger**: the anchor is recorded as verified on `1.4.5.8+24893155` only.

## Known limitations

- **Lazily compiled.** The method does not exist until a pylon placement has been attempted,
  so the cheat honestly reports "matched nothing" until then. Auto-restore's retry loop and
  the spec-036 build gate both already tolerate that, and the cheat's note says so.
- ~~Teleporting to each of two same-type pylons was not separately exercised.~~
  **Resolved the same day**: the maintainer confirmed travelling between two pylons of the
  same type. The teleport UI distinguishes them by position, as the recon expected.
- **Multiplayer is untouched** by construction: `NetPlaceEntityAttempt` still enforces one
  per type.

## Result

Gates pass. Approved for commit and tag `v0.29.0`. Spec 037 COMPLETE.
