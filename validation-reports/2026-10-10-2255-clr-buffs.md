# Validation Report — potion buffs under .NET Framework (spec 052, slice 17)

**Date**: 2026-10-10 22:55
**Commit**: uncommitted (working tree on `main` at 3eb20a0)
**Status**: PASSED
**Scope**: the `potions` and `fishing-buffs` commands renew the player's effects
under .NET Framework. The buff reader now takes its array offsets from the entry
instead of fixed mono constants, and the two commands gate on a per-feature
`WriteBuffs` instead of the full-write flag.

## What changed

- `internal/buffs/buffs.go`: `Buffs` carries the two buff-array references (from
  statLife) and the szarray header offsets; `NewFor(entry, mem, life)` takes them
  from the entry. `New` keeps mono's numbers for the package's own tests. The
  methods read `b.typePtrOff`/`b.timePtrOff`/`b.arrLenOff`/`b.arrDataOff` rather
  than the package constants.
- `internal/layout/table.go`: `PlayerFields` gains `BuffType/BuffTimeFromLife`;
  new `WriteBuffs` feature.
- `internal/layout/entry_mono.go` / `entry_netfx.go`: each gains the two buff
  offsets (mono from `BuffType/BuffTimePtrOff`; netfx `0x0C8/0x0CC − 0x470` from
  CLRFields). The netfx entry's write features gain `WriteBuffs`.
- `internal/service/potions.go` / `fishing.go`: build the reader with `NewFor`
  and the entry.
- `internal/cli/sell.go` (`potions`) / `fishing.go` (`fishing-buffs`): gate on
  `gameWriting(WriteBuffs, force)` instead of `game(true, force)`.

## Why per-feature, not the Writes flag

The buff write lands a type and a time in the player's two buff arrays, whose
offsets the entry now carries, so it is one more entry-driven write path like the
cheats and item edits. Gating it on `WriteBuffs` lets it run under the CLR while
`Writes` stays false (the flag that would claim *every* write path is ported).
The `fishing` gear command writes bait and rod fields and still needs the broader
access, so it is left on `game(true, …)`.

## Phase 4: Code quality

The buff reader is now entry-driven, matching inventory and projectiles. `New`
is kept as the mono-default constructor the package's tests use, so no test
churn beyond the one new CLR test. No duplication; the offsets are set once per
constructor.

## Phase 5: Security review

- No hardcoded secrets; none added.
- No new subprocess or network calls. The writes are two words (a type and a
  time) into the player's own buff arrays, bounded by the array length the game
  reports (checked `0 < n <= 256`). No untrusted input reaches the offsets.
- The commands ship off; a buff is written only when the player runs `potions`
  or `fishing-buffs`.

## Phase 5.5: Release safety

- **Change type**: code (a write path) plus additive version-table data.
- **Pattern**: additive — a new feature, two new player offsets, a new write
  feature on the netfx entry. The buff reader's constructor changed, but `New`
  stays for the tests and `NewFor` is the new entry-driven one.
- **Rollback**: these are renew-only writes the game counts down on its own; a
  buff stops being renewed and lapses within seconds. Revert the commit and
  rebuild to remove the path. Minutes, no data heroics.
- **Rollout**: off until the player runs the command.
