# Validation Report — terrariabonker v0.41.0

**Date**: 2026-08-28
**Scope**: Auto-selling — a whitelist of item types turned into coins, paid into the piggy
bank (spec 048).

## Summary

One new cheat, built entirely out of reads and writes: no code patch, no stub, no arena
slot. The game's own `Player::SellItem` is not called, because the whole transaction is
"clear a slot, credit some coins" once the price formula is known — and the price formula
is four lines.

720 tests pass. Twenty-two mutations run against this release's changes, **twenty-one
caught on the first attempt and one survivor**, which is part of what is worth reading.

The other part is that this cheat crashed the game once, and the audit that followed found
three defects -- one of them a rule this repo already had a scar for.

## The crash

The game died while the maintainer opened a chest with auto-sell running. **The cause was
never established**: the managed crash log had no entry for that day and `dmesg` no segfault
line, which is what a native write into reclaimed memory looks like and equally what several
other things look like. What follows is what the audit found, not a diagnosis.

**Writes went through addresses read earlier -- the rule in AGENTS.md, broken.** Both coin
paths read every slot in a container and then wrote back to the addresses that read had
returned, dozens of syscalls later, twice a second. *Locate by identity on every access,
never by a cached address; mono's GC moves objects, and a stale pointer writes into whatever
now lives there.* Opening a chest is exactly the allocation that moves objects. Every write
now re-resolves its slot and refuses when the type or stack there is not what the caller
believed, so an unexpected pre-value aborts the round instead of being overwritten.

This is the likeliest cause and it is fixed on its own merits regardless of the crash.

**Coins could be written outside the slots the game uses for them.** The round treated
`Player.inventory` as 59 uniform slots. `SellItem`'s own IL bounds its coin loop at 53, and
slot 58 is not a normal slot -- the panel's own grid hides it. Selling now walks 0..57 and
coins go only to 0..53.

**A container guard went in, and came back out.** A guard on `Player.chest` skipped any round
while a container UI was open. The maintainer found what it cost: Terraria keeps the piggy
bank *open* while the player is in range, so nothing sold while standing at the bank --
which is where loot gets sorted. It was also over-scoped, blocking writes to any container
when the race concerns only the one being drawn. Removed at the maintainer's direction. The
offset (0x0A8C, -1 none, -2 piggy bank) was validated live before removal and is recorded in
the spec; the race itself remains unmeasured.

## The part worth reading

**A credit can be arithmetically correct and still leave a state the game never produces.**
The first live sale was right in every respect the tests checked: 89,516 copper reported,
89,516 copper gained, four Slime Staffs gone, two of them prefixed and priced individually.
Every value-conservation test passed.

It left a stack of exactly **100 Silver Coin** in the bank. `Player::DoCoins` promotes a
stack that reaches 100 into 1 of the next denomination, so "100 silver" is not a thing
Terraria writes — the bank was *worth* the right amount while holding a shape the game
would never leave. No amount of "is the total right" testing finds this; it was visible
only by reading the coins back and recognising the shape as wrong.

`_normalize_coins` now does what `DoCoins` does, verified against that very stack in the
live bank: silver 100 → gone, gold 81 → 82, total 13,827,853 before and after, **delta 0**.

**One surviving mutant, and it was a weak test rather than an equivalent mutant.** The
world-scan fallback was covered by a test that relocated a single tile object — which
leaves a one-tile run the *fast* path still reads correctly, so the fallback never
executed and deleting it entirely passed. Rewritten around a bulk read that comes back
short (a run crossing the end of a mapped region, which is the real trigger); the mutant
now dies. Recorded because the first version read exactly like coverage.

**The expensive check turned out to be cheap, and the spec had predicted the opposite.**
Deciding whether a Piggy Bank is placed in the current world needs a whole-world tile
search. One read per tile extrapolated to **13.2 s** and would have killed the feature.
But tile objects are pool-allocated 24 bytes apart and contiguous down a column — a
1200-tile column measured 1197 deltas of exactly 24, 3 runs, no nulls — so reading each run
in one go and striding the type out scans 5,040,000 tiles in **0.15 s / ~16k reads**. The
`Player.chest == -2` fallback held in reserve was not needed.

That contiguity is an allocator observation, not a guaranteed layout, so `find_type`
verifies the stride as it goes and falls back to per-tile reads. A future build costs
speed, never correctness.

**A prefix scales `Item.value`.** Three Slime Staffs in one inventory read 100000, 189062
and 58522. Pricing from the item *type's* template — the obvious implementation — would
have mispriced every modified item. The price is read off the live item.

## Recon

Three offsets, asked of the mono runtime with `tools/monofields.py` on 1.4.5.7+24893155 and
then confirmed against live data, because a runtime dump only proves the runtime agrees
with itself. `--verify` reported every existing constant correct in the same session, so the
instrument was known good.

| Offset | Field | Live confirmation |
| --- | --- | --- |
| `0x124` | `Item.value` | Copper 5, Silver 500, Gold 50000, Platinum 5000000 |
| `0x0E0` | `Player.bank` | four banks at E0/E4/E8/EC, each `item[]` 40 long |
| `0x008` | `Chest.item` | as above |

The coin values pin the formula end to end: `value // 5` returns exactly one of each coin,
so `Item.value` is held at five times the copper worth and the division in `SellItem` *is*
the sell rate.

Read offline from `Terraria.exe` with `tools/ilrecon`, no game running:

- `Player::SellItem` takes **no NPC argument and checks none** — the shopkeeper gate is
  entirely in the UI (`Main.OpenShop` → `Main.npcShop` → `ItemSlot.HandleShopSlot`).
- `GameContent.NPCInteractions::Initialize` registers one `OpenShop(npcType, shopIndex)` per
  shop NPC, which is the authoritative sellable set. **Not shipped**: an NPC requirement
  breaks an established character taken to a fresh world, which is when the influx is worst.
- `DoCoins` reads coin types 71–74 and promotes at 100.

## Live verification

On 1.4.5.7+24893155, against the maintainer's own game.

- **Sale**: Slime Staff (1309), four across three slots including two prefixed. Bank
  13,738,337 → 13,827,853 copper, **+89,516 exactly as reported**. All three slots empty
  afterwards; no Slime Staff left in the inventory.
- **Reachability**: resolved as `placed` — the scan found the Piggy Bank tiles at
  (2114, 311) and (2115, 311), two tiles because a Piggy Bank is 2x1 furniture, with the
  player standing beside it at (2111, 309). Confirmed by the maintainer against the screen.
- **Promotion**: verified against the live 100-silver stack; total unchanged, delta 0.
- **Panel**: the maintainer whitelisted items from the inventory grid and confirmed they
  are auto-sold.
- **`Player.chest`**: reads -1 with nothing open, confirming the offset before the guard
  that used it was removed.
- **Not verified in game**: the zero-value trash path (no valueless item was in the
  inventory at the time), and the crash-hardening under a deliberate chest-open stress
  test. The latter rests on extended live use without recurrence, which is weaker evidence
  than the criterion it closes.

## Two design faults the maintainer found, not the tests

**Zero-value items could not be sold.** `sell_price` returned 0 and the round skipped them
as "worthless", so whitelisting a junk drop did nothing. For a junk drop "sell it" and "bin
it" are the same request; a whitelisted item worth nothing is now taken and pays nothing.
The sell list is therefore a delete list for valueless items, which the README says
plainly. The favorite override no longer depends on the item being worth something -- a
real risk when the price check moved, and M20 exists because of it.

**The whitelist was add-only in the panel.** Adding is a right-click in the inventory grid;
removing was too, which cannot work, because a whitelisted item is sold on the next tick and
never stays in a slot long enough to right-click twice. The only way out was the CLI. The
Effects panel now lists every whitelisted type with its icon and removes one on a
double-click, independently of whether the player owns one.

Both were found by using the thing. Neither would have been caught by any test written
against the spec, because the spec described the same design.

## Code quality

`_credit_coins` and `_normalize_coins` are separate: crediting decides *where* value goes,
normalising decides what *shape* it takes, and folding them together was what hid the
missing promotion behind a passing total.

## Security review

- No new runtime dependencies; `requirements.txt` unchanged, so no `pip-audit` run.
- No `eval`/`exec` of dynamic input (the only `exec(` in the diff is `QMenu.exec`, Qt's
  modal loop), no shell strings, no network calls, no secrets.
- Writes go to the player's own inventory and bank chest in their own single-player game.

## Release safety

**Rollback**: one feature commit, revertible on its own. The cheat ships switched off with
an empty whitelist, so a revert is a no-op for anyone who never enabled it.

**Not reversible by the tool**: a sold item is permanently gone once the world saves. This
is the first cheat here that destroys player property as its normal operation, which is why
favorite-protection is treated as a correctness requirement rather than a convenience, and
why the coins are credited *before* the item is taken.

## Known gaps

- Selling is priced at the flat shop rate. The Discount Card (×0.8) and NPC happiness
  (`PriceAdjustment`) are not applied: `currentShoppingSettings` is only populated while a
  shop is open, so out of shop it holds stale data and would need its own measurement.
- Writing coins into the bank while the Piggy Bank UI is **open** may race the game's own
  slot handling. Untested — called out rather than claimed either way.
- Favorite protection is covered in one ordering. The flag is read off the live item inside
  the round, so both orderings are the same code path; a second test would assert the same
  execution twice.
- **The container race is unmeasured and now unguarded.** Writing into a container's slots
  while its UI is open may race the game's own slot handling. The guard that would have
  prevented it was removed for the behaviour it cost. If a crash recurs while a container
  is open, this is the first place to look.
- The zero-value trash path has not been exercised in game.
