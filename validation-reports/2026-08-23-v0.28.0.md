# Validation Report — terrariabonker v0.28.0

**Date**: 2026-08-23
**Scope**: Spec 036 — tell the user, loudly, when the game has updated. Plus the version
detection rewrite that exposed the need for it, and recording 1.4.5.8 as a supported build.

## Summary

Terraria updated from 1.4.5.7 to 1.4.5.8 at 12:19 while the game was running, and the panel
said nothing — it could not, because its version check was reading a stale JSON blob out of
the heap and reporting the previous build with confidence. Three things came out of that:
the version is now read from the exe the process maps, an unrecognised build raises a dialog
instead of a small amber banner, and 1.4.5.8 is recorded as verified.

## The part worth reading

**The version check was wrong at the root.** It counted version-shaped strings in the
process and took the most numerous, which assumes the game's version is the one that appears
most. Measured on the live game, it is not:

- For ~21 seconds after launch the only candidates are a `1.4.5.8` constant in the exe and
  mono's own `v2.0.50727`, **one occurrence each** — a tie broken by scan order. That is the
  reported failure: "Terraria 2.0.50727 differs from 1.4.5.7 ... the offsets are almost
  certainly wrong", which aborted auto-restore for the whole session.
- On the 1.4.5.8 build the heap holds **four** copies of a stale
  `"Version":"v1.4.5.7","GitSHA":""` JSON against **one** copy of the real literal, so the
  vote returns the previous version permanently.

Two intermediate fixes were shipped and both were insufficient, which is worth recording:
filtering the runtime string stopped the abort but left the detector reporting 1.4.5.8 for
21 seconds of every launch, and the "require two occurrences" rule that followed made the
second failure *worse* by preferring the stale count-4 string. The maintainer asking whether
the game had updated is what turned up the actual answer.

The authority is the version constant compiled into the exe the process maps — Terraria.exe
contains exactly one — read after confirming, by inode, that the mapping still refers to the
file on disk. Steam replaces that file while the game runs the code it already loaded, and
in that window the file describes a build the process is not executing. The memory scan is
kept as the fallback for precisely that window, where it is the correct source.

**The gate.** An AOB is derived against one exact build, so an update means one of three
things — every pattern still matches, some do, or none do — and the user could not tell
which. A cheat that silently does nothing looks like a cheat that is off. The panel now
asks, offering to resolve every anchor without patching.

Two distinctions the design turns on:

- **Accepted is not verified.** A build this machine accepted means the byte patterns still
  match; a build in the ledger means somebody watched each cheat work. Different files,
  different wording, and the dialog says so in as many words.
- **Not yet compiled is not broken.** Several cheats hook methods mono compiles lazily, so a
  scan at the main menu reports them unmatched. The gate waits for a player to be in-world;
  a dialog that calls a cheat dead when it is merely uncompiled is worse than no dialog.

**1.4.5.8 recorded as supported.** All twelve cheats resolved on it and the maintainer
confirmed them working in-game, so `KNOWN_BUILD_KEY` moves to `1.4.5.8+24893155` and the
anchors claim it. The old `1.4.5.7+24893155` entry is kept with a warning attached: it is a
*mixed* key, version from the running 1.4.5.7 process and buildid from the already-updated
manifest, describing a build that never existed. Dropping it would silently un-verify the
work recorded under it.

## Phase 3 — Tests

- **341 passed** headless, up from 326.
- `tests/test_build_gate.py` (14): all-clear offers one-click accept; a dead cheat is named
  with its reason; Exit always offered; **closing the window is not consent**; decisions
  remembered per build and not covering others; degraded records which cheats are dead;
  forgetting brings the question back; a corrupt file is not fatal; an unknown build asked
  about exactly once *across a completed check*; a recognised build asks nothing; continuing
  disables exactly the dead cheats; an unreadable check is asked again rather than assumed
  fine; the gate waits for a player.
- `tests/test_version_detect.py` (11): the exe literal is the authority; a runtime path in
  the exe ignored; no single answer gives none; the exe beats a heap of stale strings; a
  replaced exe falls back to memory; and the fallback's own rules.
- `tests/test_build_ledger.py`: invariants restated now `KNOWN_BUILD_KEY` names 1.4.5.8 —
  "a later anchor must not inherit the default" is asserted against the *derivation* build,
  and every build any anchor claims must appear in an explicit allowlist, so adding one is a
  deliberate edit beside the claim it makes.
- **Mutation checks**: trusting the heap first fails the stale-strings test; removing the
  plausibility filter fails two; accepting on window-close fails the consent test; removing
  the asked-once record fails its test — *after* that test was rewritten, because it first
  passed with the bookkeeping gone (the in-flight guard masked it).

## Phase 4 — Code quality

- The dialog is handed a finished check and returns a decision. Everything privileged
  happens before it opens, which is what makes it testable without a game.
- `Patcher.probe` is separate from `details`: one answers "would these patterns match", the
  other "what is applied". An applied injection overwrites its own anchor, so conflating them
  would read as a pass for the wrong reason.
- Acceptance state lives in its own module beside `profile`, same atomic-write-under-lock
  shape, and is disposable.
- flake8 clean on changed code; the same three pre-existing hits remain in untouched lines.

## Phase 5 — Security review

- No `eval`/`exec`, no `pickle`, no shell, no network, no new dependencies. `pip-audit
  2.10.0`: *No known vulnerabilities found*.
- **No new memory writes.** `build-check` resolves anchors and patches nothing; the gate
  only ever disables cheats.
- Two new allowlisted ops (`build-check`, `accept-build`), both explicit-argv like the rest.
  `accept-build` takes a constrained choice and a list of cheat names, and writes only to the
  user's own config directory.
- The version read now opens the game's exe read-only and compares an inode; no write, no
  execution.

## Phase 5.5 — Release safety

- **Rollback**: `git revert`. The accepted-builds file is disposable — deleting it only
  brings the dialog back.
- **Behaviour change worth noting**: `KNOWN_BUILD_KEY` moving to 1.4.5.8 means a 1.4.5.7
  install now classifies as a hotfix rather than exact. It still proceeds, with a warning.

## Known limitations

- **A resolving anchor is not a working cheat.** The check proves a byte pattern matches, not
  that the code around it still means the same thing. The dialog's wording is deliberate:
  "the patterns still match", never "verified".
- **The JIT ambiguity is reduced, not removed.** A cheat whose method is never called during
  the session reads as unresolved however long the gate waits.
- **`build_key()` still mixes two sources** — version from the process, buildid from the
  manifest — so they disagree between an update and a restart. The gate now surfaces that
  rather than hiding it, and the ledger carries a note, but the underlying mix remains.
- **Queen Slime's sprite colour** stays as-is, shelved with the maintainer (spec 035).

## Result

Gates pass. Approved for commit and tag `v0.28.0`. Spec 036 COMPLETE.
