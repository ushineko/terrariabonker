# Validation Report — terrariabonker v0.30.1

**Date**: 2026-08-23
**Scope**: Withdraw the default-pruning shipped in v0.30.0. It destroyed real item edits.

## What went wrong

v0.30.0 recorded an item edit only where the value **differed from the item's own default**,
so that an item whose only change was a prefix would stop being reported. The baseline came
from `content.find_item_templates`.

That scan identifies the ContentSamples table by shape — one object per type — and it can
select a **live, edited** item as the template for a type. The cached template for Boomstick
read `damage 30, use_time 12, use_anim 12, auto_reuse 1`: the maintainer's own edit. Every
field of that edit therefore "matched the default" and was pruned.

**It cost eight saved entries**, and then, after the maintainer re-made a Boomstick edit to
test the feature, it silently ate that edit's use-time and use-animation too — leaving
`{"damage": 31}` where the user had set three fields.

**The verification I ran was circular.** I checked each pruning decision against the same
template source that had caused the pruning, and reported "11 entries became 1, every
decision verified". A fresh scan of memory shows the real Boomstick template is
`damage 14, use_time 40` — nothing like the cached value I had trusted.

The maintainer caught it: *"so, the slime whip and boomstick were both edited with use time
and damage, and they got dropped..."*

## What changed

- The comparison is **gone**. Everything restorable the dialog submits is recorded,
  redundant or not. A redundant field costs a harmless rewrite of a value the game would
  have set anyway; a dropped one costs the user's work, silently.
- Nothing in auto-restore consults the item templates any more, so a wrong or contaminated
  template cannot lose an edit.
- The rest of spec 038 stands and is unaffected: only the regenerated fields are recorded
  (not type, stack or prefix, which the game persists itself), edits are keyed by item type
  rather than slot, every copy is restored, and an item you are not carrying is reported as
  waiting rather than as a failure.

## Data recovery

A backup of the profile was taken before the migration. All eight pruned entries were
restored from it, and the mangled Boomstick entry was rebuilt from the live item's actual
values. Verified by running restore: Slime Whip back to damage 45 from the 15 it had drifted
to, Boomstick 31/12/12, Book of Skulls 45/12/12.

## Tests

- **353 passed.** The pruning tests are replaced by their opposite:
  `test_a_recorded_edit_is_never_pruned_against_a_template`, which records a four-field edit
  and asserts all of it survives while type/stack/prefix are still dropped.
- **Mutation check**: reinstating a pruning step fails that test.

## Known limitations

- **The template contamination itself is not fixed** — it is a separate and larger bug. The
  same scan feeds the Compendium, which means an item you have edited can be displayed with
  your edited values as its base stats. Auto-restore no longer depends on it; the Compendium
  still does. Tracked for the next spec.

## Result

Gates pass. Approved for commit and tag `v0.30.1`.
