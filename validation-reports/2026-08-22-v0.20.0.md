# Validation Report — terrariabonker v0.20.0

**Date**: 2026-08-22
**Scope**: Spec 029 — live inventory sync and the stale-write guard. Two commits: the guard
(`575af2d`), then the `serve` worker, locate caching, and the 1 Hz GUI sync.

## Summary

The GUI's inventory grid was a snapshot refreshed only by the Refresh button and 600 ms after
an edit, and editing a stale slot was destructive: `_apply_item_edit` compared against the
cached type, so a same-type edit sent cached stats, `Service.set_item` saw the live type
differ, treated it as a type change, and templated the remembered item over whatever the slot
really held.

Two fixes, deliberately independent. `Service.set_item` gained `expect_type`, which refuses
the write before touching memory when the slot no longer holds what the caller believed (or
cannot be read at all). And the grid now follows the game at 1 Hz, which was not previously
affordable: locating the player is ~99% of a read's cost and every GUI action spawned a fresh
CLI process that paid it again.

## Measurements (live game, 59 slots)

Where a read's time went, before:

| step | cost |
| --- | --- |
| `find_players()` scan | 962 ms |
| `resolve_local_player()` scan | 1434 ms |
| reading all 59 slots | 2.3 ms |
| `inventory --all --json` round trip | 2734 ms (median of 6) |
| `status --json` round trip | 3432 ms |

The 2 s status timer meant the app was already burning ~172% of one core continuously with
overlapping scans, before any sync was added.

After, same machine and game:

| | before | after |
| --- | --- | --- |
| inventory request | 2734 ms | 3.1 ms (median of 10, warm) |
| status request | 3432 ms | ~3 ms warm |
| GUI + worker at idle | ~172% of a core | 2.50% (measured over 10 s) |

First request after start still pays one cold locate (~2.8 s); everything after it is warm.

## Phase 4 — Code quality

- The expensive and cheap halves of `resolve_local_player` are now separate
  (`find_localplayer_anchor` / `local_player_at`), which is what makes the cache
  self-correcting: the anchor is found once, and reading through it re-resolves
  `Main.player[myPlayer]` every time, so a GC that moves the Player object is handled.
- `_read_block` became public `read_block` (needed outside `locate.py` for validation); dead
  code from the split removed.
- The worker reuses the existing argparse dispatch rather than defining a second op
  vocabulary, so `gui/client.py`'s argv builders are unchanged and `test_view_parity` still
  guards the one contract.
- `changed_rows` is a pure function in `invgrid`, unit-tested, so the no-flicker rule is not
  buried in widget code.
- flake8 clean at the project's ~100-col convention on all changed files. Four pre-existing
  violations left untouched (`cli.py:450`, `main_window.py:274`, `client.py:19`,
  `test_locate.py:4`).

## Phase 5 — Security review

- **New long-lived root process** is the material change. Mitigations: subcommands are
  allowlisted (`SERVE_OPS`, memory/game ops only — no `gui`, `freeze`, `godmode`, `read`,
  `write`, `serve`), a refused command never reaches the dispatcher, arguments are
  argparse-validated, argv is explicit (no shell, no `eval`/`exec`), stdout carries only the
  JSON protocol with stderr separated, and it exits on stdin EOF so it cannot outlive the GUI.
- Privilege is not widened: anything the GUI can ask the worker to do, it could already do by
  spawning `sudo -n terrariabonker …` itself, which is what it did before.
- **Dependency scan**: `pip-audit 2.10.0` against `requirements.txt` — *No known
  vulnerabilities found*. (`requirements.txt` is unchanged by this work; the scan is recorded
  because Ralph Phase 5 requires it per code change, not per dependency change.)
- No secrets, no network, no new dependencies. Config writes (`profile.json`,
  `patches.json`) go to the same user-owned paths as before, under the same `sudo -E`.
- The guard is itself a safety improvement: an unreadable slot now fails closed rather than
  being written.

## Phase 5.5 — Release safety

- **Rollback**: `git revert`, either commit alone — the guard does not depend on the worker.
- **Degrades, not breaks**: the worker is opt-in at runtime. No passwordless sudo, failed
  start, or worker death falls back to the pre-existing one-shot spawn path, and the 1 Hz sync
  is gated on the worker being available so it can never fall back to polling 2.7 s spawns.
- **Additive API**: `expect_type=None` preserves the previous `set_item` semantics, so the CLI
  contract is unchanged for scripts.

## Review pass (Codex, read-only, spec-aware)

Six findings on the working tree; five accepted and fixed, one declined.

- **P1 — cache accepted without ground truth** (`service.py`). `_blocks_valid` trusted a name
  match when `_resolve_live()` returned None, but a GC'd Player object can still read back as
  the same named player, so writes could land on dead copies. Now no ground truth means
  rescan. Regression test added.
- **P2 — dead anchor raised instead of signalling** (`locate.py`). A cached anchor that stops
  reading yields None, which fed straight into the next read as an uncaught `TypeError`
  (verified on a live pid). `_resolve_live` re-finds the anchor only on a None return, so this
  broke every served request instead of relocalizing. Operands are guarded; two regression
  tests added.
- **P2 — stacked edit dialogs** (`main_window.py`). Qt pumps events during a modal, so a
  double-click during the cold first read (~2.8 s) opened a second dialog over the first. A
  pre-dialog in-flight flag now admits one at a time.
- **P2 — sprites never repainted after extraction** (`main_window.py`). A regression from the
  no-flicker diff: after an extraction the rows are byte-identical, so no cell repainted and
  the freshly decoded icons never appeared. `_invalidate_icons()` now clears the rendered
  snapshot along with the icon caches.
- **P2 — dependency scan not recorded**. Run and recorded above.
- **Declined — one-shot read before the dialog when the worker is down.** Spec 10a
  deliberately falls back to the cached row; a one-shot read is ~2.7 s and would freeze the UI
  before every slot click on a machine without the worker. The write-time guard is what makes
  editing a possibly-stale row safe, which is the point of the two-part design.

## Known limitations

- TOCTOU is bounded, not eliminated: check and write happen microseconds apart in one process,
  and an item moved inside that window is still mis-written. Inherent to editing a running
  game's memory.
- The guard is type-only by design; stack/damage/prefix drift does not block a write, because
  those are values the user is explicitly setting.
- Cache validation is heuristic (every cached address still reads back as the same named
  player, and the live player is still one of them). A rescan is forced when either fails.

## Result

All gates pass. Approved for commit and tag `v0.20.0`.
