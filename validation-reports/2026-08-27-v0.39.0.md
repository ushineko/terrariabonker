# Validation Report — terrariabonker v0.39.0

**Date**: 2026-08-27
**Scope**: Four bugs reported from play — one of which was silently disabling the whole
trainer for anyone wearing mana gear — plus spec 046 (modifiers apply their effects), and
recon toward a projectile editor that is deliberately shipped as documentation and a tool
rather than a feature.

## Summary

Every item in this release started as something the maintainer noticed while playing. The
suite was green before each one and green after, which is the recurring finding of this
project: 615 headless tests against a synthetic memory image cannot see a wrong offset, a
wrong tab, or a value the game overwrites a frame later.

617 tests pass. Ten mutations were run against this release's changes; nine were caught
immediately, and the tenth exposed a real hole in how offsets are tested — see below.

## The part worth reading

**The trainer was silently writing to nothing, for any player with mana equipment.**
`locate.valid_block` demanded `statMana Max == Max2` to accept a candidate player block.
But `Max2` is the *equipment-adjusted* cap: a player wearing a mana flower or a meteorite
set has `Max2 > Max` permanently, so their real player block failed validation and the
locator settled on an inert load-time snapshot instead. Writes went into it and did
nothing. The rule is now a bounded inequality (`m <= m2 <= m + headroom`, same for the max
pair, and `mana <= mmax2`) rather than equality.

This is the most serious bug in this release and it presented as "nothing happens" — the
failure mode with the worst signal-to-noise, because it looks like the game changed rather
than like a bug.

**A modifier assigned in the editor was cosmetic** (spec 046). `Item.Prefix` multiplies the
item's own fields and stores the results; the byte at `+0x15C` is only what the tooltip
reads. The trainer wrote the byte alone, so every modifier it assigned was a name.

The fix had **two halves**, and the first alone produced "it only works the first time":

1. The stats were never written at all. Now recomputed from the ContentSamples template
   base — never from the item's current values, so re-applying cannot compound to ×1.32.
2. The dialog submitted *every* field on every OK, populated from the item's current stats.
   Those echoes counted as explicit edits, which by the spec's own ordering land after the
   modifier and overwrite it. Only fields the dialog does not carry (knockback, scale,
   shootSpeed, mana) ever survived — exactly the shape of "it worked, sort of, once."

The dialog now sends only the fields the user actually changed. That was worth fixing on
its own: pressing OK on an untouched dialog previously rewrote every field of the item.

The lesson, recorded in the spec: "explicit edits win over the modifier" is right only if
*explicit* means the user typed it. **An echo is not an edit.**

**The 82-entry multiplier table is generated, not transcribed.**
`tools/extract_prefix_stats.py` reads `Item::TryGetPrefixStatMultipliersForItem` out of the
game's IL → `data/prefix_stats.json`, 78 modifiers, spot-checked against the wiki. Nine
stats × 82 prefixes is precisely the sort of table that gets one digit wrong by hand and is
then believed.

**`crit` at `0x150`, pinned in-game rather than predicted.** Declaration order *suggested*
it; two Goblin Tinkerer reforges of a Minishark *settled* it (0 → 3 for Sighted, then 3 → 5
for Demonic — from base, not compounding). `armorPenetration` and `bonusTagDamage` were
predicted the same way and are **still not written**, because no modifier rolled granted
one and neither was ever observed. `apply_prefix_stats` reports them in `skipped`, and a
test asserts Godly reports `crit` as skipped rather than dropping it quietly. An unverified
offset written into an item cannot be undone.

Those reforges also corrected a documented claim: an item keeps a trainer's edits through
its *first* reforge and loses them at the second, because the game resets to defaults only
when it has an existing modifier to strip. That explains the Molten Hamaxe seen at
v0.38.0 with its Legendary knockback applied but base damage.

**Two smaller ones, both reported from play**: pick power 250 could not break orichalcum or
anything above it (now 1000), and the Effects panel was not remembered between sessions —
saving the window size wrote a fresh state dict over the saved effects instead of merging.
The recipe dialog now opens at the size of its recipe.

## The mutation that survived, and the hole it found

| Mutation | Outcome |
|---|---|
| a player wearing mana gear is rejected again | caught |
| pick power back below the orichalcum tier | caught |
| a modifier applies no stats (the reported bug) | caught |
| the dialog echoes untouched fields over the modifier | caught |
| saving the window size wipes the saved Effects | caught |
| the grid syncs against the wrong tab | caught |
| the recipe dialog stops fitting its content | caught |
| `crit` written to the unverified neighbour offset (`0x154`) | **SURVIVED** |
| `crit` written to `0x154` (after the fix below) | caught |
| `knockBack` moved one field along (`0x0B4`) | caught |

The survivor is the interesting one. **No test in the suite could tell `0x150` from
`0x154`**, because every test reads the offset from the same constant the code writes
through — the synthetic memory image is built from `inventory.ITEM_CRIT` and then read back
through `inventory.ITEM_CRIT`. The assertion was self-referential, and would have stayed
green while the trainer corrupted a real item permanently.

Two tests were added in response: one pinning the offsets as **literal values** with each
one's in-game evidence in the docstring, and one asserting that the two unverified offsets
are still not in the write set. Both mutations are caught now.

The general form is worth carrying forward: *a constant cannot be validated by a test that
reads it from the constant.* Offsets derived from the game need their evidence asserted as
a literal, or they are untested no matter how many tests touch them.

## Projectile recon (no feature shipped)

Toward a per-item projectile editor, using the Book of Skulls as the live subject. Seven
offsets were solved — not by memory diffing, but out of `Projectile.SetDefaults`' own
declared values, after the maintainer asked the question that reframed the whole effort:
*"why don't you look at the IL to see what the weapon actually does?"*

`tileCollide 0x100`, `friendly 0x0D0`, `aiStyle 0x0B0`, `timeLeft 0x0B4`, `penetrate 0x0D4`,
`alpha 0x098`, `extraUpdates 0x104`. `hostile` is explicitly **not** pinned: it sits in a
three-way tie, and a field that reads one value everywhere pins nothing.

`tools/projectile_probe.py` is shipped for the maintainer to run themselves, because every
attempt to co-ordinate "fire now" against a probe window failed. It enforces values every
pass (a fast weapon reuses slots between polls, so patch-on-new-slot missed nearly
everything), offers `--ab` slot parity as a control, and reports displacement rather than
velocity — a projectile pinned against a wall keeps a velocity vector while going nowhere.

**Its one result is explicitly incomplete.** A patched-vs-control run gave 30.7% vs 0.9%
of samples inside solid tiles, and that A/B **has no null control run** — the same probe
with no field writes, to show the split is not an artifact of slot parity itself. It is
recorded in `docs/item-fields.md` as a correlation, not a finding. Parked at the
maintainer's request.

Also corrected from the previous release: the "the stub cannot cast" finding was withdrawn
in v0.37.0, and this cycle produced its own retractions — `timeLeft` was retracted on one
live reading and then un-retracted against 242 IL declarations, and several probe reports
were simply wrong about what the maintainer was firing (reading `oldPosition` at `0x20` as
`position`, and detecting by slot occupancy, which misses fast weapons entirely).

## Tests

617 pass (`pytest`, headless, synthetic memory image — no game, no root). Up from 584 at

(`cli.py`, `client.py:19`, `test_locate.py:4`).

## Security review (Phase 5)

- No `eval`/`exec`, no sockets, no network calls in shipped code.
- No hardcoded credentials.
- Dependencies unchanged since v0.34.0; `pip-audit` not re-run.
- `tools/extract_prefix_stats.py` runs `dotnet` with an explicit argv list and no shell.
  It is a developer tool, not shipped code, and reads a local game file.
- **New writes to the save**: prefix stat fields on items. This is the release's real risk
  surface — item stats persist, so a wrong offset corrupts an item permanently rather than
  failing a test. Mitigated by verifying `crit` in-game before writing it, by refusing to
  write the two offsets that remain unverified, and by the literal-offset test added above.
- `tools/projectile_probe.py` writes to live projectiles, which are transient and never
  saved. It requires root and is opt-in.

## Release safety

- **Rollback**: `git revert` or the previous tag. No patch changes, no arena stamp change
  (`TBARENA2` since v0.37.0), no state-file format change — the Effects fix adds keys to
  the existing GUI state file and merges rather than replaces, so an older build ignores
  them harmlessly.
- **Not reversible by revert**: item stats already written by a modifier. Reverting stops
  further writes; it does not restore an item. Re-assigning the modifier is the repair.
- **Behaviour change**: applying a modifier now resets that item's manually-tuned stats to
  base × modifier, because a previous manual edit is indistinguishable from a previous
  modifier. Documented in spec 046 Risks; the dialog's own damage field still wins, which
  is how a tuned number is kept.

## Known gaps

Carried forward, unchanged:

- `RELEASE_ITEM_OFF` (`Player+0x67F`) is still unidentified.
- The auto-use hook's call target is identified by shape and position, not mono metadata.
- Whether switching items destroys an outstanding bobber was never settled.
- `Service` and `MainWindow` remain god classes (spec 045 tiers 2–3, deferred by design).
- `service.py`'s 59 deferred imports are unchanged; the rule in `AGENTS.md` binds new code.

New with this release:

- **`armorPenetration` and `bonusTagDamage` are unverified and unwritten.** Predicted at
  `0x154`/`0x158` by the same method that got `crit` right — an argument for trying them,
  not for writing them.
- **`reuseDelay`'s offset is unknown**, so it is not scaled. It sits after six bools, so it
  is not simply `+4`. Mostly zero in practice, which is why this is nearly harmless.
- **The projectile A/B has no null control**, and `tileCollide=1` forced on live skulls did
  not visibly change their collision. Both open; the editor is not started.
